A concept refresher for the Legacy Notice Manager workshop

Copilot supports the testing process; a human remains responsible for the decision. This is a fictional workshop, not a production or maritime safety system. Source: README.md:3-7; workshop/README.md:8-16.

01 / the system

Explore a synthetic, imperfect system

Create and manage fictional notices.

Documentation and tests are incomplete.

Investigate what is known and what is not.

Introduce the notice register and the create, review, and export journey. The app and its data are synthetic. Do not reveal facilitator outcomes. Source: README.md:3-7; workshop/README.md:8-12.

02 / Copilot context

Choose the right kind of guidance

Instructions

Standing guidance

Prompt

A repeatable task

Agent

A specialist role and boundaries

Skill

A reusable method

Tools

Capabilities, when available

Point to the corresponding files under .github. Support and automatic discovery vary by Copilot host; pasting reviewed instructions into Chat is a fallback. Source: COPILOT-CUSTOMISATION-GUIDE.md:3-12.

03 / observe

Start with what you can observe

Observed

What happened?

Expected

What source supports it?

Unknown

What needs a human answer?

In the demonstration, record the action and result before reading the source. An unexpected result is not automatically a confirmed defect. Source: workshop/labs/lab-07-explore-the-application-in-a-browser.md:25-36.

04 / test

Make one focused test

  1. Choose one observed behaviour.
  2. Find a source for the expected result.
  3. Review the proposed test before running it.

Use the smallest appropriate test level and synthetic data.

For browser tests, inspect the fixture, locator strategy, and assertions. Do not invent an expected result when the requirement is unclear. Source: workshop/labs/lab-08-create-and-run-playwright-tests.md:25-45.

05 / review

A failure is a signal, not a verdict

  1. Product, test, environment, or ambiguity?
  2. Inspect output and any saved screenshot or trace.
  3. Record a human decision before changing the app.
A passing test also does not establish that an expectation is approved policy. If the test passes, screenshots and traces may not be available; the optional failure demonstration is intentionally failing, not a product defect. Source: TEST-STRATEGY.md:18-24; EVIDENCE-GUIDE.md:3-7.
